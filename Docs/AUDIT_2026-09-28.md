## Runtime model and risk selection

`bootstrap.js` owns the disposable intro and then evaluates application scripts sequentially. The menu resolves enabled worlds and loads level definitions for adventure counts. Menu launch starts temporary graphics settings. `selectLevel()` loads a definition, overlays editor state where applicable, normalizes it, prepares decoded character and level imagery, prepares ambient systems, and commits `level` and `state` together. Intro completion records replay history; movement routes end in shared interaction handlers. Question handlers own completion, learning records, and challenge effects. Earned exits asynchronously fade into a reward; connected levels call `selectLevel()` again. Explicit replay mutates the existing state object. Menu return invalidates loading and disposes renderers, effects, ambient work, and active images.

Rendering has several owners: DOM artwork/sprites; legacy Canvas scene effects; Canvas or WebGPU challenge effects; the shared Cinematic runtime for Illustrated shadows/particles/full-scene contributions; experimental Voxel; and Three worlds. GPU acquisition and recovery cross the shared capability broker. Authored settings, temporary play settings, graphics preferences, challenge saves, learning reports, asset caches, and service-worker caches have distinct lifetimes.

The highest-risk seams selected for deeper investigation were:

1. Reusing state at reward/replay and restoring only part of it after reload.
2. Successful versus failed asset promises and their release ownership.
3. Renderer handoffs and hidden/abandoned asynchronous work.
4. PWA activation/cache ownership and differences from worker-blocked browser tests.
5. Tests written before deferred bootstrap, which can stop before reaching their claimed invariant.

## Finding 1 — Earned replay retains the exit lock

Severity: **Medium**. Confidence: **Reproduced**.

Evidence / reproduction: Complete all three Stella Montis challenges through their answer controls, activate the exit, select **Speel nog een keer**, then continue the intro. The scene has zero completed runes but `exitTransitionPending === true`; all three challenge buttons are disabled. Reproduced in desktop Chromium and iPad landscape WebKit. No debug completion was used; arrival handlers selected challenges/exits, and actual UI controls answered every question and restarted the level.

Root cause: `transitionToReward()` sets the flag at `src/app.js:4478`. `restart()` at line 4534 resets progress on the same object but never clears it. Interaction guards and hotspot rendering at lines 4101, 6604, and 6638 continue honoring that stale flag. A fresh `selectLevel()` creates a new state, explaining why ordinary first entry works.

Production impact: A normal completed-adventure replay cannot interact with challenges or exits. The same shared path serves terminal levels. Leaving the level and entering a fresh state is a recovery path; no loss of earned completion was established.

Recommended remediation: Reinitialize transient transition state through the existing level-state lifecycle when restarting, preserving the explicit restart/save semantics.

Recommended verification: Earn a final reward without debug shortcuts, replay through the visible button, walk to and solve a challenge, and repeat. Exercise both motion preferences and desktop/touch layouts. Calling `showReward()` directly is insufficient because it bypasses the flag setter.

## Finding 2 — Resuming a level drops earned score counters

Severity: **Medium**. Confidence: **Reproduced**.

Evidence / reproduction: Answer one four-question challenge correctly in LVL-0035, reload, then answer the remaining eight questions correctly. Before reload the save contains `answered:4`, `firstTryCorrect:4`, `attempts:4`. Re-entry restores the completed challenge but initializes all counters to zero. Final saved/reward totals are **8 answers, 8 attempts, 67% correct**, although all 12 answers were correct. Reproduced in Chromium and iPad landscape WebKit with real answer controls.

Root cause: `createLevelState()` restores `completedRunes` but hardcodes score counters to zero (`src/app.js:541–579`). `saveChallengeProgress()` and `saveCompletion()` subsequently overwrite persisted totals from these partial counters; `getAccuracy()` divides by the full level question count.

Production impact: Ordinary interrupted play produces misleading reward statistics and overwrites these aggregate fields. Challenge completion itself resumes correctly. This finding does not establish loss of the separate question-level session report or progression unlocks.

Recommended remediation: Restore validated counters for the same matching unfinished run that supplies completed challenges. Preserve fresh-run behavior after earned completion and explicit restart.

Recommended verification: Compare uninterrupted and reload-between-challenges runs, including wrong answers, help, legacy saves, changed challenge signatures, and completed-run replay. Check saved totals and visible reward text.

## Finding 3 — Optional image failures survive network recovery

Severity: **Medium**. Confidence: **Reproduced in Chromium with real HTTP requests and independently through the production coordinator**.

Evidence / reproduction: Execute the production asset cache and readiness coordinator with an optional animal image returning HTTP 503 for all three attempts. Activate the otherwise-ready level, release it, restore the network, and prepare it again. The second plan still marks the image failed, with **three total requests**, not a new request. The rejected entry remains in `images` across release.

The browser reproduction used the actual LVL-0001 `assets/ambient/animals/owl/owl-open.png` URL: exhaust 503 retries, enter the scene, return to menu, restore successful responses, and re-enter. Both plans report that image failed, still with **three total requests**. `renderAmbientAnimal()` (`src/app.js:6527`) omits animals without a ready open frame.

Root cause: `src/ambient-system.js:93–160` memoizes the rejected promise. `src/asset-readiness.js:110–134` retains/releases only successful plan images on normal activation and menu cleanup. Failed optional assets are absent from that set, so later preparations reuse the rejection. Required-asset failure takes a separate cleanup path and should not be conflated with this defect.

Production impact: A transient outage can disable an animal image or other optional visual for the remainder of the page session despite recovered connectivity and repeated navigation. Reloading the page resets this in-memory cache. This is recovery failure, not permanent authored-asset loss.

Recommended remediation: Give rejected entries an explicit retry/eviction lifecycle while preserving in-flight deduplication and bounded retries.

Recommended verification: Exhaust retries, recover the server, navigate away/back, and confirm a fresh successful fetch and visible visual. Cover optional blink/flyby frames and required assets separately.

## Finding 4 — Worker activation deletes unrelated origin caches

Severity: **Low**. Confidence: **Reproduced by real Chromium service-worker activation and independently with the production handler**.

Evidence / reproduction: Run the unmodified service-worker activation handler against a disposable cache registry containing `unrelated-app-offline-v1` and an old Atlas cache. It deletes both.

The browser check created a real unrelated cache containing a sentinel response before Start registered the worker. After activation, only `svenadventure-static-v231-play-scene-depth-off` remained. All caches were in a disposable test browser context.

Root cause: `service-worker.js:125` deletes every cache except `CACHE_NAME`, with no Atlas ownership filter. In contrast, the app's explicit local-reset handler filters names using the Atlas prefix.

Production impact: Installing/updating Atlas on an origin shared with another application destroys that application's CacheStorage caches. No actual co-hosted application or user cache loss was established on the deployment. A dedicated origin avoids the collision, which limits the severity.

Recommended remediation: Delete only obsolete Atlas-owned cache names.

Recommended verification: Preserve an unrelated sentinel cache during real activation while removing old Atlas versions and keeping the current cache functional offline.

## Suspicious but unproven risks

- Asset fetches/decodes and level-script loading lack an application-level deadline. The preparation UI can await a stalled operation; an actual indefinitely stalled production network was not reproduced. Existing tests delay requests briefly rather than keeping them pending.
- Worker `skipWaiting()`/`clients.claim()` can replace the controller while old application scripts are running; refreshable level/config files use the network while core scripts are cache-first. No incompatible old/new release pair was available to prove a mixed-version defect.
- Reward fade continuations have no generation/cancellation check before `showReward()`. The menu action remains available during the fade. Navigation in that interval deserves a focused regression; cross-level save corruption was not reproduced or claimed.
- Physical iPad Safari/PWA memory, GPU behavior, suspend/resume, and long-duration thermal/frame pacing remain unverified. WebKit emulation and Chromium tablet configurations are not certification of those conditions.
- Firefox was not exercised; it is absent from the configured projects and the configured Playwright Firefox executable was not found by the local availability probe. No Firefox-specific conclusion is made.

## Test-quality findings

- The initial desktop selection completed with **23 passed, 11 failed, 1 skipped**. Nine challenge-active tests and two level-state-isolation tests fail before their intended assertions because they access `selectLevel`/manifest globals before activating deferred bootstrap. These are baseline failures, not audit regressions. No assertions were weakened.
- The WebKit batch completed with **36 passed and 4 failed** across landscape and portrait. The four failures are two Flyby VM tests repeated in both projects: their fake shell lacks `querySelector`, now required by the production preview path. They fail before measuring the intended lifecycle; they do not demonstrate a browser Flyby defect. Both audit defects reproduced in both orientations; diagnostic passes assert the observed faulty state, not correct behavior.
- Existing tests can enter reward directly and therefore miss the exit flag that causes Finding 1. The current graphics-session retry test restarts during ordinary play, which also avoids that flag.
- Reload/progression tests inspect completed challenge IDs without comparing aggregate counters or reward text, missing Finding 2.
- Cold-load tests cover required-image success/exhaustion; successful-image release tests do not prove recovery of rejected optional cache entries.
- Normal Playwright projects block service workers; the explicit PWA test is an exception. That test seeds an old cache name, not a running prior application/worker pair.
- Session reporting is disabled under `navigator.webdriver` unless `atlasSessionTest=1`; the audit's answer-flow probes enabled it. Many ordinary browser tests therefore do not exercise production report writes.

## Recommended remediation order

1. Finding 1: restore usable replay interactions.
2. Finding 2: preserve aggregate results across resumed runs.
3. Finding 3: recover failed optional imagery across navigation.
4. Finding 4: constrain worker cache deletion to owned caches.

## Final assessment

Atlas supports continued feature development with targeted hardening work. The verified defects are bounded and recoverable, but replay and resumed results are not currently trustworthy. Correct those flows and restore meaningful lifecycle/progression test execution before release. The tested renderer ownership/preparation paths are substantially healthier than the state-reset and failure-cache boundaries. No blanket development freeze, architectural rewrite, graphics downgrade, or visual retuning is justified by this evidence. No remediation was performed.
